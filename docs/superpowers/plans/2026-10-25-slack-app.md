# Slack App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `slack` integration app that installs via OAuth, posts alerts into picked channels, links GitHub accounts
to Slack users by exact email (or "Connect Slack"), mentions the alert's sender, and moves Webhook handles to channels.

**Architecture:** The workspace installation and the GitHub→Slack links are global tables keyed by Slack team ID, read
only through the master `db` connection; an integration's Slack app points at a workspace and owns tenant-scoped channel
handles. All Slack calls go through `proxyFetch` to `slack.com`; the bot token is KMS-encrypted (dual-stack endpoint).
Alerts reuse `buildSlackAlert` and `chat.postMessage`; send-time link resolution runs inline next to the verdict.

**Tech Stack:** TypeScript, Drizzle ORM (Aurora PostgreSQL, RLS), AWS Lambda (API, worker), `@aws-sdk/client-kms`,
Vue 3 + Radix Vue + Tailwind, Vitest, Terraform.

**Spec:** [docs/superpowers/specs/2026-10-25-slack-app-design.md](../specs/2026-10-25-slack-app-design.md), building on
[2026-10-25-integration-apps-design.md](../specs/2026-10-25-integration-apps-design.md).

## Clarifications to the spec (from the code map; binding for this plan)

- **Commit-email source dropped.** GitGazer stores no commit emails and cannot tie a commit author to the sender's
  GitHub account; the spec allows dropping it. Sources are `gitgazer_email`, `github_profile_email`, `slack_sign_in`.
- **Verified emails live in their own table** `gitgazer.github_user_emails`, keyed by GitHub user ID, never on `users`:
  `memberQueryRelations` returns whole `users` rows to every member. They are written in the Cognito attributes relay
  (`GET /api/auth/cognito/user`), which can run before the `users` row exists.
- **"Lookup when a member signs in"** is implemented as: when the relay stores a user's emails, it deletes that GitHub
  user's cached "not found" link rows, so the next alert looks them up again. No extra task.
- **Global tables are hard-restricted:** a custom migration revokes all privileges on `slack_workspaces`,
  `slack_user_links` and `github_user_emails` from `gitgazer_reader`, `gitgazer_writer` and `gitgazer_mcp`; code reads
  and writes them only through the master `db` (as `authentication.ts` does for `users`).
- **Login app is a GitHub OAuth App:** `user:email` must be requested via `var.github_oauth_scopes` (Terraform).

## Global Constraints

- Never write AWS profile names, account IDs, personal details or secrets into the repo (manifest included).
- Never apply migrations, never run `terraform apply`; agents cannot run `drizzle-kit` — ask the user to run
  `cd packages/db && npx drizzle-kit generate` (and `--custom --name=<x>` for custom SQL) and continue after.
- Never log bot tokens, OAuth codes, emails or Slack user IDs; log counts, booleans and GitGazer IDs.
- All Slack HTTP calls go through `proxyFetch` to `https://slack.com/api/...` (already on the `http-proxy` allowlist).
- KMS client: `new KMSClient({useDualstackEndpoint: true})`; region from `AWS_REGION`, never hardcoded.
- Value sets are `as const` tuples with derived types (repo convention).
- Slack user IDs become `<@…>` only if they match `/^[UW][A-Z0-9]+$/`, and only after escaping.
- Comments only for a non-obvious why; mirror neighbouring code; English everywhere in the repo.
- Commits: one line `type: description`, no scope, no trailers. Delivered as a gh stack (one branch per Task group).
- Tests: `pnpm nx run @gitgazer/<project>:vitest:test --output-style=static --skip-nx-cache -- --project unit --run <path>`
  for backend projects; `pnpm nx run @gitgazer/web:test:run --output-style=static --skip-nx-cache` for web; plus
  `pnpm nx run-many -t typecheck lint pretty:check -p <projects>` and `cd apps/web && pnpm exec vue-tsc --noEmit`.

## Review Focus

1. Two integrations share a workspace and one removes its Slack app → the other keeps sending; the token is revoked only
   by the last one (Task 5 test `uninstall keeps the token while another integration uses the workspace`).
2. The token is revoked in Slack → the first failing send marks the workspace disconnected, writes one event-log entry
   per integration using it, and later alerts skip Slack handles without calling Slack (Task 8 tests).
3. A rate-limited or failing lookup → the alert goes out without a mention and no "not found" is cached (Task 7 test
   `lookup failure neither mentions nor caches`).
4. Sender missing, a bot, or `dependabot[bot]` → no lookup and no mention (Task 8 tests `missing sender is not looked
up` and `bot sender is not looked up`).
5. One rule pointing at a Webhook handle and a Slack handle → both delivered; only the Slack message carries the mention
   (Task 8 test `mentions only on Slack handles`).
